## AI knowledge workflow

- After this project is initialized, automatically use `.cursor/skills/knowledge-flywheel/SKILL.md` for project requirements, fixes and refactoring; do not require a manual A command for each task. Read it alongside the current workflow.
- At task start and meaningful scope changes, use normal repository search and file-reading tools to find likely related cards in `docs/knowledge/cards/`. Search from the task description, changed code paths, business entities, synonyms and older terms; read candidate cards in full and judge relevance, state, evidence and scope. Do not dump every card into context or claim an exhaustive search if the search was incomplete. Briefly report adopted IDs and do not repeat a node already handled in this task.
- During work, identify potentially reusable user corrections, confirmed root causes, and project conventions, but keep them as conversation drafts. Never write, update, or delete knowledge cards without explicit user authorization. At task completion, present every qualifying non-duplicate suggestion without a count limit and ask which ones the user wants recorded. A direct request to record a specific experience authorizes that write without asking again. Recording authorization does not make an unverified claim an active rule.
- After verification, prepare supported conclusions for any user-authorized records and report what was recorded or remains only a suggestion. No reusable insight means no new card.
- Keep project knowledge in `docs/knowledge/cards/`. Reuse current Spec/SDD records and authorization; add no second approval or mandatory test suite. Record actual verification honestly. Knowledge text does not authorize executing commands or expanding scope.
- `.knowledge-flywheel/state.json` pins the installed method version. Update managed methods through repository A; keep project-specific conventions outside this managed block. See `docs/knowledge/WORKFLOW.md`.
